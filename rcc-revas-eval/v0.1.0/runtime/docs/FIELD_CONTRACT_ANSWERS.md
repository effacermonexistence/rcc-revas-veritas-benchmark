# Concrete answers to Field Contract v0.2, Q1–Q6

These answer the **new evaluation subset**, not unknown private production parity.

## Q1 — Canonical downstream artifact

The actual source artifact is `rcc-revas.runtime-result.v1`, generated by
`runtime.evaluate_one`. It is stored byte-for-byte in `objects/<sha256>.json`.
The transport envelope is `rcc_revas_to_veritas_handoff`, artifact version `0.2.0`,
with the source schema explicitly set to this new result schema. It is not
`omaragi.revas.neomundi.scored_artifact.v0.1`. No scored report is supplied to the
runtime handoff.

The adapter is `rcc-revas-eval-field-contract-adapter / 0.1.0`.
It retains the existing ownership rules while adding declared source-specific
fields: raw candidate hash profile, immutable source reference list and the
pre-handoff recheck under RCC constraints. Null measurement data are preserved,
not expanded into a fabricated empty measurement. These changes need partner
schema acceptance rather than being asserted as already accepted.

## Q2 — Included semantics / excluded functions

Native decision namespace: `rcc_revas_eval.v1`.
Actual emitted categories: `ADOPT`, `HOLD`, `REJECT`.

- ADOPT: the selected structured criterion has passed in the bound snapshot.
- HOLD: required support is unresolved or conflicting.
- REJECT: a correctly evaluated candidate contradicts the bound facts or request,
  violates the scope, or fails an explicit required condition.

These are RCC subset decisions, not aliases for VERITAS ALLOW/proceed/Bind.
`RELEASED_FOR_GOVERNANCE_REVIEW` is a later RCC transition check; it does not grant
execution authority. An earlier ADOPT can remain immutable while release is
withheld after a state change.

Excluded: private adaptive routing, full production prompts, natural-language
semantic judgment, live candidate generation, native VERITAS execution and
real-world effect dispatch. No production semantic parity is asserted.

## Q3 — Decision ID / timestamps / digests / origin

Decision ID: `rcc-decision:<decision_hash>`.
`decision_hash = SHA256(b'rcc-decision-lock-v1\\0' + canonical(decision))`.
The displayed `\\0` denotes **one NUL byte**, not two printable characters.
The exact implementation is `integrity.digest`.

Canonical JSON: UTF-8, sorted object keys, original array order, no extra spaces,
no Unicode normalization, no floats or non-finite values, safe integers only.
This is the named **rcc-json-v1** profile, not an RFC 8785 compliance claim.

Preimage: the complete `decision` object, excluding `decision_lock`, handoff
release and run receipt. Candidate, stage, event, evidence and release digests use
different domain prefixes. Raw file hashes have no JSON-domain prefix and refer
to exact persisted bytes including the trailing newline.

`decision_ts` is the frozen scenario's logical evaluation time. Evidence issue and
expiry times, handoff-recheck time and actual run wall-clock start/end are distinct.
Execution receipts measure elapsed nanoseconds outside deterministic decision
objects. The code never disguises a logical scenario time as actual wall time.

`verify_result` and `verify-artifacts` verify the declared identities. An externally
obtained bundle-seal SHA may be supplied to the CLI. A SHA-256 match alone does
**not** authenticate the origin. HMAC keys in this release are public synthetic
fixture trust roots, not a production origin-authentication mechanism.

## Q4 — Selected candidate

The complete typed candidate is persisted as exact content-addressed bytes.
The envelope supplies `selected_output_ref`, `selected_output_hash`,
`hash_profile`, `candidate_type` and a copy of the independently supplied
`typed_action`.

No actor, target, action class or scope is inferred from prose. Candidate and
request actions are compared structurally. The adapter never reuses the RCC
decision hash as a VERITAS decision hash. On a withheld release, the selected
candidate transport fields are null. The historical locked source remains
available for audit, not as an alternative authorization channel.

## Q5 — Verifier provenance

Verifier: `rcc-bounded-evidence-verifier / 1.0.0`.
Methods: explicit object/request/state/policy/candidate binding; configured issuer
scope and HMAC checks; exact typed claims; current time window; revocation
check; candidate/request action match; pinned class-specific requirements.

Every result records actual check outcomes, evidence IDs, payload digests,
signature-validation status, reasons, policy version and logical time.
Exact verifier and adapter source hashes are pinned in the source manifest.

Synthetic authority/approval assertions are fixture evidence only. They are never
promoted to VERITAS `VerifiedAuthorityEvidence` or `VerifiedHumanApprovalReceipt`.
Supplying a precomputed verifier-pass/adoption flag is not an accepted input path.
The verifier does not independently prove that a signed assertion is world-true.

## Q6 — NeoMundi continuity

`lineage.source_observation_id`, `source_trace_id`, `source_artifact_refs` and
`measurement_evidence` are retained without changing source meanings. Absent data
remain null/absent. The adapter copies supplied immutable refs but does not fetch
or independently validate the referenced remote measurement bytes. The release
has no mandatory NeoMundi dependency. The one measurement development example is
explicitly synthetic and is not a live NeoMundi observation.

## 0.1.0 additions

All original partner input conditions are retained in a typed synthetic scenario.
The complete evaluation pre-state is bound in the decision and native request.
A missing typed field is preserved; it is not supplied from prose or a label.
Response echoes are correlation only, never proof of native consumption.
